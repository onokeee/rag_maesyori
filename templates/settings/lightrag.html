LightRAGへの入れ方

このアプリで作った Markdown(.md) を LightRAG に手作業で入れるときの手順と、サーバー側の推奨設定です。LightRAG 1.5.7 を主な対象にし、1.4.x との違いを注記しています。

{% call ui.card("1. サーバーのバージョンを確認する") %}

GET /health の応答でバージョンを確認します。バージョンによってファイルの扱いが違います。

項目1.5.x（主な対象）1.4.x
文書ID（doc_id）ファイル名の MD5内容の MD5
同じ名前のファイルHTTP 409 で断られる。変更したファイルは先に削除してから入れ直す内容が変われば別の文書として入る（古い方は手で削除）
エンティティ種別ENTITY_TYPE_PROMPT_FILE（YAML）。ENTITY_TYPES を書くと起動に失敗するENTITY_TYPES 環境変数（リスト）

このアプリのファイル名は、同じ帳票・同じ期間なら毎回同じになります（入れ替えの手順が単純になります）。

{% endcall %} {% call ui.card("2. サーバーの .env を設定する（最初に1回）") %} 
SUMMARY_LANGUAGE=Japanese
ENTITY_TYPE_PROMPT_FILE={{ download_name }}
  • SUMMARY_LANGUAGE=Japanese: 既定は English。英語のままだとエンティティの説明や検索キーワードが英語になります。
  • ENTITY_TYPE_PROMPT_FILE（1.5.x）: 下の「設備保全向けのエンティティ種別」YAML を PROMPT_DIR/entity_type/ に置き、ファイル名を指定します。既定の種別には 設備・部品・原因・処置 がありません。
  • 埋め込みモデルは日本語に強いものを最初に決めて固定します。途中で変えると全件の入れ直しになります。
  • 数万件を入れる場合は、PostgreSQL などのストレージを使います（既定のファイル保存は小規模向け）。
{% endcall %} {% call ui.card("3. 分割（チャンク）の設定") %}

一覧表の記録ファイルは、ヒントを付けて入れてください。取り込み設定の「ファイル名に LightRAG の分割ヒントを付ける」をオンにすると .[{{ hint_records }}] が付き、サーバーの設定に関係なく記録1件が1つの断片に収まります（ヒントの説明）。

サーバーの設定一覧表の記録ファイル帳票・集計ファイル・データセット説明
ヒントを付ける（推奨）記録1件が1つの断片。途中切れなし—（ヒントは付けません）
LIGHTRAG_PARSER 未設定使えません。1,200トークンの固定幅で機械的に切られ、記録の2〜6割が途中で切れます。日本語の文字の途中で切れて文字化け（�）を含む断片もできます問題ありません（1件＝1断片）
*:native-teP,*:legacy-R（env.example のまま）ヒントがなければ見出し・段落の単位で最大2,000トークン。記録は切れません問題ありません
サーバー全体を legacy-R(chunk_ts=800)記録が途中で切れますやめてください。長い帳票が2つに分かれます

当社サンプル（一覧表3種・約46,000件）での実測: LIGHTRAG_PARSER 未設定だと記録の 21〜61% が途中で切れ、T1 では 6,011断片中323件に文字化けが出ました。ヒント（chunk_ts={{ hint_chunk_ts }}）では途中切れ 0 件です。

  • 帳票: ヒントは付けません。短い帳票は1件が1つの断片に収まります。明細表（交換部品・点検項目の表）を読む帳票は 1,200トークンを超えて2つ以上に分かれることがありますが、長い項目の見出しに識別子（## 点検項目（AGV-811 Fab1 AGV））が入るので、どの帳票の断片かは分かります。明細表の行だけで埋まった断片には識別番号が出ません。
  • ヒントを付けても外しても文書ID（doc_id）は同じです。付け外しして入れ直すときは、古いファイルを先に削除してください（1.5.x は同名だと 409）。
  • 「設備×年月ごと」に分ける設定は、ファイル数が7〜8倍になり処理も少し増えます。設備の列がきれいな番号で、設備ごとに入れ替えたい場合だけ選んでください。
  • 1ファイルに入れる記録の上限（既定300件）は、分割のされ方には影響しません。LightRAG での削除・入れ直しの単位として決めてください。
  • 投入後、文書の状態（doc_status）の parse_engine / chunk_opts で、実際にどう分割されたかを確認できます。
{% endcall %} {#- ヒントの文字列と数値は core/naming.py の LIGHTRAG_HINT_RECORDS から表示する（値を変えたら説明も追従する） -#} {% call ui.card("ファイル名の分割ヒント（.[…]）とは", id="filename-hint") %}

LightRAG は受け取った md をそのままは使わず、一定の長さ（トークン数）の断片（チャンク）に切ってから、断片ごとに AI で設備・現象・部品などを抜き出します。

LightRAG 1.5.x では、ファイル名の末尾（.md の直前）に .[…] で指示を書くと、そのファイルだけ、サーバーの初期設定ではなくその指示どおりに分割します。

トラブル対応一覧_2024-04.[{{ hint_records }}].md
部分意味
legacy読み込み方。md をテキストのまま読みます（表を AI で解析するなどの処理をしません）。
R分け方。空行 → 改行 → 句点（。）の順に、なるべく区切りのよい場所で切ります。
chunk_ts={{ hint_chunk_ts }}断片1つの最大の長さ（トークン数）。
chunk_ol={{ hint_chunk_ol }}前の断片と重ねる長さ。0 なら重ねません（重ねると同じ記録が2つの断片に入ります）。

なぜ付けるのか

同じ md でも、切られ方はサーバーの設定しだいで大きく変わります。

  • LIGHTRAG_PARSER を設定していない: 1,200トークンの固定幅で機械的に切ります。記録の途中で切れたり、日本語の文字の途中で切れて文字化け（U+FFFD）を含む断片ができたりします。
  • サーバーの設定例（env.example）をそのまま使っている: 見出し・段落の単位で、最大2,000トークンずつ切ります（native-P）。

ヒントを付けると、サーバーの設定に関係なく、アプリが意図した切り方にそろえられます。

記録が途中で切れると、後ろ側の断片に管理No・設備・日付が入らず、「どの設備のいつの話か」が分からない断片になります。そうした断片は検索しても正しく使われません。そのため chunk_ts は、記録1件がまるごと収まる長さにしてあります。

このアプリでの扱い

  • 一覧表の取り込み設定で「ファイル名に LightRAG の分割ヒントを付ける」をオンにすると、記録ファイルの名前にヒントが付きます（新しい取り込み設定では既定でオン。記録ファイルを入れるなら、そのままオンを推奨）。集計ファイルとデータセット説明には付けません。
  • 帳票には付けません（多くは1件が1つの断片に収まり、分かれる場合も見出しに識別子が入るため）。
  • 元の値に含まれる .[ や [ ] はファイル名から取り除きます。意図しないヒントと解釈されて、アップロードが断られるのを防ぐためです。

注意

  • LightRAG 1.5.x の機能です。1.4.x では分割の指定として効きません。
  • 1.5.x は文書ID（doc_id）を決めるときにヒントを外すので、ヒントを付ける／外す・数値を変えても同じ文書として扱われます（同名として 409 になるため、入れ直す前に LightRAG から削除してください）。
  • ヒントを付けたファイルでは、サーバーの LIGHTRAG_PARSER に書いた処理オプション（例: 表の AI 解析 t）がヒントの内容で丸ごと置き換わります。
  • ヒントの書式が正しくないと、アップロード時に HTTP 400 で断られます。
  • 実際にどう分割されたかは、文書の状態（doc_status）の parse_engine / chunk_opts で確認できます。
{% endcall %} {% call ui.card("4. 件数・ランキング・推移は集計ファイルで答える") %}

LightRAG は質問ごとに数十件程度の記録しか読みません。「今年いちばん止まった設備は？」「月ごとの件数は？」のような質問は、記録ファイルだけでは正しく数えられません。

一覧表の取り込みで作られる 集計ファイル（…_集計_月次_…、…_集計_設備別_…）と データセット説明（…_00_データセット説明.md）も一緒に入れてください。数値はアプリで計算済みです。

{% endcall %} {% call ui.card("5. 更新するときの手順") %}

このアプリは投入済みのファイルとの差分を管理しません。取り込みごとに、その取り込みの全ファイルを zip で渡します。

  1. 一覧表の完了画面で Markdownをまとめてダウンロード（zip） を押します。
  2. 同じファイル名のものが LightRAG に入っていれば、LightRAG で先に削除します（1.5.x は同じ名前だと 409 になり、入れ直せません）。
  3. LightRAG の処理が終わる（idle になる）のを待ちます。
  4. zip の RAG投入用/ のファイルを LightRAG に入れます。管理用_RAGには入れない/ は入れません。

帳票は、確定し直したものだけを「削除してから入れ直す」で更新します。

{% endcall %} {% call ui.card("6. 保存先フォルダを LightRAG の入力フォルダにする", id="save-folder") %}

設定 → 保存先フォルダに LightRAG サーバーの入力フォルダ（INPUT_DIR。WORKSPACE を使っているときは INPUT_DIR\ワークスペース名）を指定すると、完了画面の［保存先フォルダに保存］で md をそこへ直接書けます（ダウンロードと同じく、アプリからはデータが消えます）。

  1. 入れ替えるファイル（同じ名前の文書）が LightRAG に入っていれば、LightRAG で先に削除し、処理が終わる（idle になる）のを待ちます。1.5.x は文書をファイル名（末尾の .[…] を除く）で見分けるので、削除しないまま同じ名前で入れても、スキャンで取り込まれず __parsed__ に移されるだけです（LightRAG の中身は古いまま）。 この削除では「アップロードされたファイルも削除」にチェックを入れます（API では delete_file=true）。入れないと __parsed__ に古いファイルが残り、アプリが同じ名前とみなして保存を止めます（そのときは __parsed__ の古いファイルを手で消します）。
  2. アプリで［保存先フォルダに保存］を押します。同じ名前のファイルがフォルダか __parsed__ にあると、既定では何も保存せずに名前の一覧を出します。
  3. LightRAG の文書の画面で［スキャン］を押します（コマンドなら POST /documents/scan）。取り込み終えたファイルは LightRAG が __parsed__ フォルダに移します。

保存したあとで古い文書を LightRAG から削除するときは、逆に「アップロードされたファイルも削除」にチェックを入れないでください（delete_file=false）。チェックを入れると、LightRAG は同じ名前のファイルを直下と __parsed__ の両方から消すので（1.5.7 の document_routes.py の delete_file_variants_by_file_path）、いま保存したファイルも消え、アプリにもデータが残っていません。

スキャンは入力フォルダの直下のファイルだけを読み、サブフォルダの中は読みません（1.5.7 の document_routes.py の iter_new_files）。管理用のファイル（正規化データ・問題一覧・取込レポート）を保存する設定にすると、サブフォルダ _管理用_RAGには入れない に入るので、LightRAG には入りません。
