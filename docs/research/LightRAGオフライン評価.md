# LightRAG 1.5.7 オフライン評価（アプリの実出力 Markdown）

作成日: 2026-09-17 ／ 対象: 現行アプリのコードが実際に出す Markdown（帳票 F1〜F5、一覧表 T1・T2・T5）
LLM・API は一度も呼んでいない。チャンク分割・トークン数・ファイル名解釈・重複判定は LightRAG 1.5.7 のソースの関数をそのまま使い、
エンティティ数だけは LLM なしの推定値である。

再計測: `scripts/eval/lightrag_offline_eval.py`（使い方は 7章）。

## 1. 方法

### 1.1 出力の作り方（アプリのコードをそのまま呼ぶ）

| 対象 | 作り方 | 出力 |
|---|---|---|
| 帳票 F1〜F5 | `scripts/samples/evaluate_forms.py` と同じく見本 3 件（版が混ざるように選ぶ）で `suggest_rows` → `rows_to_pattern`。種類名はフォルダ名から番号を外したもの（例: 設備修理報告書）。30 ファイルを `match_pattern` → `extract_document` → `export.formats.build_markdown` / `markdown_filename` | 各 30 ファイル |
| 一覧表 T1 | `open_source` → `guess_layout` → `sample_data_rows` → `suggest_columns` → `spec_from_suggestions` → `read_records` → `tables.markdown.render_all`（`tables.pipeline.render_files` と同じ引数）。**対応内容列を log 役割**にし、AI 結果なし（ルール出力のみ） | 8,095 件 |
| 一覧表 T2 | 同上（CP932 CSV、先頭の出力条件行あり）。ログ列なし | 33,095 件 |
| 一覧表 T5 | 同上（UTF-8 BOM CSV）。ログ列なし | 5,043 件 |

一覧表は次の 4 通りのファイル単位で出した。

| ファイル単位 | 内容 |
|---|---|
| `month`（既定） | アプリの出力そのまま（記録＝年月ごと・300件上限、月次集計、設備別年度集計、データセット説明） |
| `entity_month` | アプリの出力そのまま（記録＝設備×年月ごと） |
| `per_record`（シミュレーション） | `record_block` の 1 件を `# 見出し` にして 1 ファイルにしたもの（アプリにはない形） |
| `single`（シミュレーション） | 全記録を 1 ファイルに連結（集計・説明ファイルなし） |

一覧表の列の役割・表示はアプリの候補（`suggest_columns`）をそのまま使った。T1: 管理No=key、設備番号=entity、発生日=date、対応内容=log。
T2: 管理番号=key、設備コード=entity、発生日時=date。T5: 台帳No=key、対象設備=entity、起票日=date。

生成物は scratchpad の `lr_eval/md/<variant>/`（Markdown と manifest.json）。他のエージェントがコードを並行して編集していたため、
**生成は評価の最初（2026-09-17 の作業開始直後）に一度だけ行い、その時点のコードの出力を固定して計測した。**

### 1.2 分割の経路（LightRAG 1.5.7 の関数を直接呼ぶ）

| 経路 | 呼び出し | 想定する状況 |
|---|---|---|
| F_1200_100 | `chunking_by_token_size(tok, text, None, False, 100, 1200)` | サーバーで `LIGHTRAG_PARSER` 未設定（legacy＋F が既定。`resolve_parser_directives` で確認） |
| R_800_0 | `chunking_by_recursive_character(tok, text, 800, chunk_overlap_token_size=0, separators=DEFAULT_R_SEPARATORS)` | アプリの現行ヒント `.[legacy-R(chunk_ts=800,chunk_ol=0)].md` |
| R_1000_0 / R_1200_0 / R_1500_0 | 同上でサイズだけ変更 | ヒントの値の比較（R1000/R1200 は月別 3 表だけ） |
| P_2000 | `NativeMarkdownParser._extract_text` → `build_ir` → `write_sidecar` → `chunking_by_paragraph_semantic(tok, content, 2000, blocks_path=…, chunk_overlap_token_size=100)` | `env.example` の `LIGHTRAG_PARSER=*:native-teP,*:legacy-R` をコピーしたサーバー。**オフラインで動いた**（表・数式・画像なしなので t/e の LLM 呼び出しは発生しない） |

- トークナイザは LightRAG と同じ `TiktokenTokenizer("gpt-4o-mini")`（o200k_base）。
  **tiktoken はエンコーディングを初回にネットワーク（openaipublic.blob.core.windows.net）から取得する。** 本評価では取得済みのキャッシュ
  （`lightrag_src/tiktoken_cache`）を `TIKTOKEN_CACHE_DIR` で指定し、ネットワークなしで動かした。
- ヒントの解釈は `lightrag.parser.routing.resolve_parser_directives`、正規化後のファイル名は `normalize_document_file_path`、
  内容の重複は `lightrag.utils_pipeline.compute_text_content_hash` を使った。

### 1.3 指標の定義

| 指標 | 定義 |
|---|---|
| 記録 | 一覧表ファイルの `## ` ブロック。帳票・1件1ファイルはファイル全体 |
| 途中切断 | 記録（空白と `\` を除いて比較）が、どのチャンクにも丸ごと入っていない。帳票・1件1ファイルは 2 チャンク以上に分かれたもの |
| U+FFFD | チャンク本文に置換文字がある（F の固定トークン窓が多バイト文字の途中で切ったもの） |
| ID無し | そのファイルの記録ID（管理No/管理番号/台帳No、帳票は正解データの report_id）がチャンクに1つも出てこない |
| 設備/日付無し | 設備番号・設備名（大きいファイルは英数字の設備番号だけ）がない、または日付（YYYY-MM-DD 等）がない |
| 見出しだけ | 空でない行がすべて `#` で始まるチャンク |
| 推定エンティティ | LLM なしの粗い推定: 見出し数＋英大文字コード（例 CMP-103、PC12-1115）＋固有名になりやすい項目値（設備・工程・区分・部署・判定など）の異なり数。LightRAG の上限 `MAX_EXTRACTION_ENTITIES=40`（constants.py:27）と比べる |
| LLM呼出 | チャンク数×2（抽出1回＋gleaning 1回、`MAX_GLEANING=1`） |
| 入力tok概算 | 1チャンクあたり 2×(system 1,367＋user 268＋チャンク)＋継続指示 405＋1回目の出力 400（仮定）。system/user/継続は prompt.py を tiktoken で数えた値 |
| 定型行（ファイル間） | 全ファイルの半数以上に同じ行があるときの、その行のトークン割合 |
| 定型行（記録内） | 全記録の 10% 以上に同じ行があるときの、その行のトークン割合（見出し行を除く） |

制約: エンティティ数は推定であり、実際の抽出結果ではない。帳票は現行の抽出精度（F3 43.9% など）の誤りを含んだ出力で評価している。
一覧表は画面での手直し（列の除外・値の置き換え）をしていない既定の候補で評価している。

**R800 で何が起きるか（実物）**: T1 `トラブル対応一覧_2024-05.md` の R800 チャンクは
「`## 【TR-2024-00701】…` から時系列の最後まで 770 トークン」＋「`- 使用部品: …` `- 停止時間: 435分` … `- 出典: …（管理No TR-2024-00701）` の 100 トークン」の組が続く。
後ろのチャンクには設備名も発生日もなく、停止時間・状態・再発だけが孤立する（出典行があるので ID だけは残る）。
LightRAG の R は `\n\n` → `\n` の順で区切るので、800 を超える記録は必ず記録内の行境界で切られる。

**F で何が起きるか（実物）**: 同じファイルの F チャンクは「朝の巡回時、CH-A WF6流量偏差…」のように記録の途中から始まり、
先頭が `�が1.3E-6Torrまで悪化…` のように多バイト文字の途中で始まるものがある（overlap 100 でも見出しは入らない）。

## 6. 推奨（優先度順）

### 6.1 [must] 一覧表のヒントを `legacy-R(chunk_ts=1500,chunk_ol=0)` にする — core/naming.py

- 変更: `LIGHTRAG_HINT_RECORDS = "legacy-R(chunk_ts=1500,chunk_ol=0)"`。
- 根拠: 2.1 の表。R800 は T1 63%・T5 43%・T2 12% の記録を切り、切れた後半（停止時間・状態・完了日など）が設備・日付なしで孤立する（T1 4,681 チャンク）。
  LLM 呼び出しは F の 1.8〜2.1 倍、入力トークンは 1.5〜1.7 倍。R1200 でも T1 の 84 件（1,200 超の記録）が切れる。R1500 は 3 表とも切断 0・ID/設備/日付の欠落 0 で、コストは F の 0.90〜1.07 倍。
- 注意: T2 のように短い記録は R1500 で 1 チャンク 3〜5 件になり、推定エンティティが 40 を超えるチャンクが 416（3.7%）出る。6.5 のコード列の整理と組み合わせる。
  値を変えると既存のヒント付きファイルとは chunk_opts が変わる（doc_id は同じ）ので、ガイドに「入れ直す場合は先に削除」を明記する。
- 期待効果: 記録の途中切断 0、LLM 呼び出し T1 で 26,992 → 14,848（−45%）。

### 6.2 [must] 記録の大きさの上限を、ヒントの chunk_ts から実トークンで決める — tables/markdown.py

- 変更: `RECORD_TOKEN_BUDGET` を「chunk_ts − 余裕（例 100）」＝1,400 にし、6.3 の推定式で判定する。超える記録は時系列を `max_timeline_entries` より手前で打ち切る（現行の「以降N件は管理用の正規化CSVに収録」表示のまま）。
  AI 整形の要点を出す記録はさらに長くなるので、要点と時系列の合計で判定する。
- 根拠: T1 の記録は max 1,468 トークン（ルール出力だけで）。現行の予算 1500（推定値）は tiktoken で最大約 1,900 になり、R1500 でも切れうる。
- 期待効果: AI 整形を有効にしても 1 記録 1 チャンクを保証できる。

### 6.3 [must] `estimate_tokens` を実トークン以上になる式にする — core/mdtext.py

- 変更: 非ASCII 1 文字＝1.1、ASCII 2 文字＝1（`math.ceil(1.1 * non_ascii + ascii / 2)`）。docstring の「保守的」を実態に合わせる。
- 根拠: 5章。現行は中央値で 13%、最大 29% 少なく見積もる。新式は p95 0.98・最大 1.05。
- 期待効果: `HEADING_IDENTIFIER_TOKENS`（帳票の見出しに識別子を入れる判定）と 6.2 の判定が、LightRAG の実際の分割と一致する。

### 6.4 [should] 追記ログの時系列から、他の列と同じ文を省く — tables/markdown.py（`_log_lines`）

- 変更案: 時系列のエントリ本文から、同じ記録の原因・処置内容・使用部品の値と一致する文（「。」「、」区切りで正規化して完全一致）を除き、「（処置内容と同じ）」程度に縮める。または `md` 設定で「ログ列を出す場合は処置内容・原因の列を出さない」を選べるようにする。
- 根拠: 時系列が記録トークンの 47.6%。例の TR-2024-00701 では処置 5 手順・原因・使用部品が時系列 3 番に全文で再掲されている。T1 の 62% が 800 トークン超。
- 期待効果: 記録 p50 を 841 から大きく下げ（時系列の半分が重複なら 600 前後の見込み。未計測）、R1500 でも 2 件入るチャンクが増える（呼び出し減）。重複文による同じ関係の二重抽出も減る。

### 6.5 [should] 意味のないコード列を既定で出さない／置き換える — tables/mapping.py の候補、tables/markdown.py

- 変更案: 型が code/enum で値の種類が少なく（例 20 種類以下）、値が英数字 1〜4 文字の列（`状態コード` `再発フラグ` `発見区分コード` `記録区分`）は、`value_map` が空なら候補の md を `omit` にする。`value_map` があれば「状態: 完了」のように置き換えて出す（既存の ColumnSpec.value_map を使う。別名辞書は作らない）。データセット説明に「コードのまま出している列」を一覧にする。
- 根拠: T2 の記録内定型行 23.1%（`- 状態コード: 9` が 32,321/33,095 件）。コード行は文字数の 28%。P2000/R1500 で推定エンティティ 40 超が 4〜5%（コード値が数に入る）。
- 期待効果: T2 の入力トークン約 2 割減、抽出上限超過チャンクの減少、「9」「H01」のような無意味なエンティティの抑止。

### 6.6 [should] 設備の値の揺れを、集計とファイル分けの前にそろえる — tables/summaries.py（`entity_display`）／正規化

- 変更案: entity 列（型 code）の値が「CODE(名前)」「CODE 名前」の形なら、先頭の設備番号を entity の値にし、残りを表示名に回す（設備名の列がないときだけ）。
- 根拠: T5 の対象設備 257 種類 → 設備番号で 116。設備別年度集計が 877 ファイル（T1/T2 は 279）に割れ、
  `CVD-203(W-CVD_3号機)_2023年度` と `CVD-203_2023年度` のように同じ設備の件数が別ファイルに分かれる（集計の答えが誤る）。設備×年月の記録ファイルは 3,318、中央値 1 件。
- 期待効果: 集計値の正しさ、ファイル数の削減（T5 entity_month 4,196 → 約 2,000 以下の見込み）。

### 6.7 [should] 帳票: 見出し語が値になった行を出さない・ファイル名を一意にする — export/formats.py、core/naming.py

- 変更案 1: 値（正規化後）が、その帳票の種類の他の項目の候補ラベル、または辞書のラベルと一致する場合は Markdown に出さず、タイトル・ファイル名にも使わない（JSON には残す）。
- 変更案 2: `markdown_filename` は、タイトル項目に識別番号（key 相当）がない、または同じ種類の中で名前が重複しうる場合、`file_hash` の先頭 8 桁を末尾に付ける。
- 変更案 3: タイトル項目に設備も識別番号も入らないときは、元ファイル名の拡張子なしの部分をタイトルに併記する（現行は項目が空のときだけ）。
- 根拠: 同名 3/150（409）、`報告日` `復旧日時` 入りのファイル名 10/30（F1）、`- 品名: 品番` 30/30（F4）、ID がチャンクにない帳票 24/150、F5 のタイトル `# 工程異常連絡票 2023-08-13`。
- 期待効果: 投入時の 409 と上書きの防止、ノイズのエンティティ（単価・品番・起票）の抑止、検索時に帳票を特定できる率の向上。

### 6.8 [should] LightRAG ガイド（templates/settings/lightrag.html）の書き換え

「3. 分割（チャンク）の設定」を次の趣旨に更新する（design.md 1章の用語: 一覧表・帳票・記録ファイル・集計ファイル）。

- `LIGHTRAG_PARSER` を設定しないサーバーでは、一覧表の記録ファイルは **1,200 トークンごとに機械的に切られ、記録の 3〜7 割が途中で切れ、文字化け（�）を含む分割も出ます**（本評価: T1 で 6,480 チャンク中 379）。
  **一覧表の記録ファイルは、ヒントを付けて入れてください**（取り込み設定の「ファイル名に LightRAG の分割ヒントを付ける」は、新しい取り込み設定では**既定でオン**にしました。保存済みの設定はそのままの値を使います）。
- ヒントの値は `.[legacy-R(chunk_ts=1500,chunk_ol=0)]`（6.1 反映後）。1 件の記録が 1 チャンクに収まる大きさです。
- `env.example` をそのままコピーしたサーバーは `LIGHTRAG_PARSER=*:native-teP,*:legacy-R` になっており、ヒントのないファイル（帳票・集計ファイル・データセット説明）は native＋P（2,000 トークン）で分割されます。これも記録を切らないので問題ありません。
- **サーバー全体を `legacy-R(chunk_ts=800)` にしないでください**（帳票の一部が 2 つに分かれます）。
- ヒントの有無を変えても LightRAG の文書IDは変わりません（ヒント部分は名前から除かれる）。付け外しして入れ直すときも、先に削除してください。
- 「設備×年月ごと」はファイル数が 7〜8 倍になり、処理コストも少し増えます。設備の列がきれいな番号で、設備ごとに入れ替えたい場合だけ選んでください。
- 1 ファイルに入れる記録の上限（既定 300）は、分割の結果には影響しません。LightRAG での削除・入れ直しの単位として決めてください。

### 6.9 [consider] その他

- **native-P を推奨経路として併記する**: 3 表とも途中切断 0、呼び出しは F の 0.78〜0.83 倍で最少。ただし P は 1 チャンクに記録を最大 5〜7 件詰めるので、短い記録（T2）では推定エンティティ 40 超が 4.6%。6.5 の後に再評価する。
  P チャンクの `heading` メタデータは先頭ブロックの見出しだけなので、2 件目以降の記録の識別は本文の `## 【管理No】…` 見出しと `- 管理No:` 行に依存する（現行出力はこれを満たす）。
- **1件1ファイルは作らない**（2.2）。ファイル数と、R800 で見出しだけのチャンク（T1 5,499）が出る形（`_Block` がタイトルと本文を空行で分けるため）になる。どうしても作るなら見出しと本文の間に空行を入れない。
- **月次集計・設備別年度集計のコード値**（T2 の「故障区分コードの内訳: （空欄） 161件、F01 8件」）も 6.5 と同じ置き換えを使う — tables/summaries.py。
- 計測スクリプトを、出力仕様を変えるたびに回す（`scripts/eval/lightrag_offline_eval.py`、7章）。帳票は種類の定義を手で直した状態でも測る。

### 8.7 残っている課題

- **明細表を含む帳票が複数チャンクに割れる**（新規）。表の行だけのチャンクに識別番号がない。対策候補: 明細表の各行に設備番号を付ける、帳票にもヒントを付ける、`## 見出し` を明細表の途中にも繰り返す。いずれも出力仕様の変更なので、利用者の了承がいる。
- **T2 の native-P で推定エンティティ40超が 415 チャンク**（4.1%）。P は1チャンクに記録を4〜8件詰めるため。ヒント（R1500）なら 4 チャンク。
- **T1 の記録が 1,200 トークンを超えるものが 23 件**。ヒント（1,500）では切れないが、AI整形の要点を出すとさらに増える（6.2 の予算で自動的に時系列を削る）。
- **コード列を出さない判定は見出しの語（コード・区分・フラグ）に頼っている**。見出しがコードらしくない列（例「状態」で値が `9`）は拾えない。`value_map` を設定した列は、画面で出す設定に戻す必要がある。
- T5 の「設備/日付無し」は測り方の限界（2.1 の注）。
