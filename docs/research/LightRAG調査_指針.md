
## guidelines

- [must/both] 1レコード（帳票1件、表1行）は、それ単体で読んで意味が通るように書く。帳票種別、管理番号/報告番号、設備番号＋設備名、ライン/工程、発生日（ISO）を毎レコードの本文に入れる。ファイル冒頭に1回書くだけでは足りない。
  理由: 抽出LLMはチャンク本文しか見ず、ファイル名もメタデータフィルタも使えない。P の見出し文脈はプロンプトには入るが、埋め込みには入らない。Anthropic Contextual Retrieval では、文脈を前置すると検索失敗が35-49%減った。
- [must/tables] 一覧データを Markdown パイプ表で出力しない。1行を『### {管理番号}｜{設備名}（{設備番号}）｜{日付}』の見出し＋『- 列名: 値』の連続行（空セルは省略）で書き、レコード間は空行1つにする。
  理由: 1.5.7 の native パーサはヘッダー行をチャンクから落とし（extract.py:527-541、#3950）、F/R では2チャンク目以降に列名が残らない。key:value 形式は STC 論文（arXiv 2605.00318）で MRR が改善した。
- [must/tables] 1レコードの内部には空行を入れない（複数行の文章は改行のみ）。レコード間だけ空行にする。
  理由: R の区切りは \n\n が最優先で（constants.py:105-115）、空行区切りなら実測でレコード境界どおりに分割された。native P でも、段落の空行は結合時に捨てられるだけで害はない。
- [should/tables] 表データのチャンクは1チャンク3-8レコード（約400-800トークン）を初期値にし、実験で決める。チャンク設定はファイル名ヒントで固定する（例: トラブル対応一覧_2024-04.[legacy-R(chunk_ts=800,chunk_ol=0)].md）。対応内容が長いレコードは1件で1チャンクになってもよい。
  理由: 抽出の上限が40エンティティ/100件（constants.py:26-27）なので、P2000（約16件）では欠落し、1件1チャンクだと呼び出しが2回×件数になる。サーバーの LIGHTRAG_PARSER に依存しないよう、ヒントで経路を固定する（routing.py:1420、ヒントが最優先）。
- [should/forms] 長文テキストを含まない帳票はヒントを付けず、1帳票1チャンク（1200トークン未満）に収める。1200トークンを超えうる帳票では、各『##』セクション見出しにも識別子を入れる（例: ## 修理内容（R2026-00123／EQ-001 CMP装置／2026-09-14））。
  理由: 実測では F/R/P のどれでも約500トークンの帳票は1チャンクになる。分割されると後続チャンクから設備や日付がわからなくなる（#3234）。
- [must/both] ファイル名は論理文書に対して安定かつ一意にする。DBの連番ではなく、報告番号やソースExcelの file_hash 先頭など、再登録しても変わるものに依存しない値を使う。例: 設備修理報告書_R2026-00123.md、トラブル対応一覧_2024-04.md。
  理由: 1.5.7 の doc_id はファイル名の MD5（pipeline.py:999）で、同名は409（document_routes.py:5148）。DBリセット後に 00001_… が別の文書を指すと衝突するか、誤って別文書と誤認される。
- [must/both] 出力ファイル名から '.[' と ']' を除去または置換する（ヒントを付けるのはアプリが意図した場合だけ）。制御文字も除去する。
  理由: routing.py:62 のヒント正規表現に一致すると、不正なヒントは HTTP 400 になり、正しい形でも経路が変わる。document_routes.py:180-320 は制御文字と / \ : を拒否する。
- [must/both] 値にも NFKC をかける（現在は項目ラベルだけ）。設備番号・設備名・人名・部署名は辞書で正規形に統一し、全帳票・全一覧で同じ表記にする（例: ＥＱ－００１→EQ-001、ﾎﾟﾝﾌﾟ→ポンプ、『山田 太郎』→『山田太郎』）。
  理由: エンティティ統合は名前の完全一致だけで、LightRAG の正規化は不完全（カタカナ間の空白や半角カナが残る、utils.py:5391、#1323、#1726）。表記ゆれがあるとノードが分裂する。
- [should/both] 設備コードは必ず自然言語名と併記する（『CMP装置（EQ-001）』）。可能ならマスタからライン/工程/設備分類も書く。
  理由: 検索はベクトルのみで BM25 がなく（#3198）、コード単体では検索されにくい。分類やラインの質問は、本文に書かれていないとグラフで扱えない。
- [should/both] 全ファイル共通の定型文と内部IDを削る。『画像の内容は解析していません…』、帳票テンプレートのバージョン、DBの文書ID、画像のセル座標（J3）がそれにあたる。出典に必要なら、末尾1行に『出典: 元ファイル名 / 報告番号』だけを残す。
  理由: 同一文面は全文書で共通のノイズエンティティやハブノードを生む（テンプレート名が数千文書に登場する）。小さいチャンクの埋め込みも似通う（現行サンプルでは末尾部分が24-41%）。source_id 200件の上限にもすぐ達する。
- [consider/both] テンプレートから決定的に1文の要約を生成してレコード先頭に置く（LLM不使用）。例: 『2026-09-14、CMP装置（EQ-001）で搬送アーム停止が発生し、原因は位置センサーのコネクタ接触不良、端子清掃と再接続で復旧した。』
  理由: LightRAG は本文に書かれた関係しか抽出しない（arXiv 2410.05779 §3.1）。箇条書きだけだと 設備-現象-原因-処置 の関係が暗黙になる。効果は実験で確認する（仮説）。
- [must/tables] 件数・ランキング・平均停止時間・月別推移・再発リストは、アプリで決定的に集計した『集計サマリー文書』として別ファイルで出力する。『集計期間』『集計日（as of）』を本文に明記し、根拠の管理番号も列挙する。
  理由: クエリ予算（CHUNK_TOP_K=20、MAX_TOTAL_TOKENS=30000、constants.py:57-64）と source_id 200件上限（operate.py:2519-2562）のため、検索では数万行を数えられない。GraphRAG 論文（arXiv 2404.16130）も参照。
- [should/both] 出力をバイト単位で決定的にする。行順・項目順を固定し、本文にエクスポート日時を入れない。追記データは既存ファイルを作り直さず、新しい期間ファイルとして出す。
  理由: 更新はすべて削除→再投入で、抽出キャッシュのキーはプロンプトのハッシュ（utils.py compute_args_hash）。削除では共有エンティティが再構築される（operate.py:1101、#3659）。
- [should/tables] AIで正規化した対応内容は、時系列の箇条書き（『- 2024-04-12 保全課 田中: シール交換』）にし、『（AI整形）』と明示する。原文を併記するかどうかは実験で決め、既定では併記しない。
  理由: 原文と整形文を両方入れるとトークンが倍になり、矛盾するエンティティも生まれうる。AIの推定値と原本の値を区別できないと、回答で誤りを事実として扱ってしまう。
- [should/both] 数値には単位を残す（『作業時間: 1.5時間』）。日付は ISO 形式に加え、必要なら『2026年9月』のような表記も1回入れる。
  理由: 単位のない数値は意味のあるエンティティや関係にならない。時系列の質問に使える手がかりは本文だけ（PR #3805 未マージ）。
- [must/forms] H1 タイトルは『最初の文字列項目』ではなく、テンプレートで指定した識別項目から作る。帳票種別＋報告番号＋設備名（番号）＋日付。
  理由: 現在は formats.py:43 で最初の string 項目を使っており、点検記録表のタイトルが『点検記録表：高橋』（人名）になっている。タイトルは P の Section Context と引用で最も目立つ。
- [should/both] 利用者向け手順書に、サーバー側の前提設定を載せる。SUMMARY_LANGUAGE=Japanese、設備保全向けの ENTITY_TYPE_PROMPT_FILE（1.5.x。ENTITY_TYPES は起動失敗）、日本語対応の埋め込みモデルを最初に固定、PostgreSQL などのストレージ、バージョン確認、投入後に doc_status の parse_engine / chunk_opts を確認。
  理由: env.example:321 は English。lightrag.py:1257-1263。README の Storage 節は既定ストレージを小規模向けとしている。process_options は投入時に固定される（FileProcessingPipeline.md:112）。
- [consider/both] 報告者などの人名を出力するかどうかを検討する（仮名化、部署名のみ、または除外）。
  理由: 既定の種別に Person が含まれ、人名が多数の設備をつなぐハブになり、偽の経路ができる。個人情報の観点もある。効果は実験で確認する。
- [consider/tables] 大量の生レコードは『!』オプション（例: .[legacy-R!(chunk_ts=800,chunk_ol=0)].md）でベクトルのみにし、KG は集計文書と帳票から作る二層構成を、コスト比較の候補にする。
  理由: '!' は抽出とグラフ書き込みを省き、ベクトルは作る（constants.py:455-458、FileProcessingPipeline.md 2.1）。数万行分の抽出コストを避けつつ、naive/mix 検索は使える。

## file_unit_options

- A. 1行1ファイル（35,000ファイル）
  +['引用がレコード単位になる（file_path=1件）', '1件の修正が削除1件＋投入1件で済む', 'チャンク境界の問題がない（1件≒120-400トークン）']
  -['抽出が 2回×行数（約7万回）で、コストと時間が最大', 'doc_status / full_docs が数万件に増え、既定ストレージでは重い', 'Web UI での手動アップロードは現実的でない', '一括差し替えでは文書ごとにKG再構築が走る（#3659, #2765）', '各チャンクが小さく、同じ設備の文脈がつながらない']
  仮説: 検索精度（単一レコードの特定）は最高だが、コスト対効果は B/C/E より悪い。100件のパイロットで、1件あたりのLLM呼び出し・トークン・時間を測れば、35k件の総コストは線形に外挿できる。
- B. 期間ごと（月別。例: トラブル対応一覧_2024-04.md、1ファイル約300-3,000行）
  +['追記データを新しい月ファイルとして出せ、過去ファイルに触れない', 'ファイル名が安定し、決定的', 'ファイル数が数十から数百で、手動アップロードもできる', '時期の質問で引用ファイル名がそのまま手がかりになる']
  -['件数の多い月は1ファイルが大きく（例: 3,000行≒36万トークン）、MAX_ASYNC_LLM=4 の直列処理が長くなる', '同じ設備のレコードが多数のファイルに分散する', '過去レコードを修正するとその月全体を削除・再投入することになる', '引用はファイル単位なので、同じ月の中は区別できない']
  仮説: 月あたり500行を超える場合は、半月・週や通番ブロック（_2024-04_part01）に分けると処理時間とやり直し範囲が安定する。レコード本文に日付を書いておけば、期間分割による検索精度の低下はない。
- C. 設備ごと（例: トラブル対応一覧_EQ-001.md）
  +['同じ設備のレコードが連続し、R/P で同じ設備のまとまりのチャンクになりやすい', '設備の履歴を質問すると、引用がそのファイルに集まる']
  -['新しい行が来るたびにその設備ファイル全体の削除・再投入が必要（追記に弱い）', '設備によってファイルサイズの偏りが大きい（ハブ設備は巨大になる）', 'ハブ設備のエンティティは source_id 200件の上限で飽和しやすい', '設備マスタの変更（名称変更など）でファイル名が不安定になる']
  仮説: 更新頻度が低い過去分のアーカイブには向くが、日々の追記がある運用では B に劣る。『設備×年』（EQ-001_2024.md）にすれば追記の影響を1年分に限定できる。
- D. 1ファイルに全件（8,000-35,000行を1つの .md）
  +['作成と投入が1回で済む', 'ファイル管理が最も簡単']
  -['35k行は約420万トークン・約3,800チャンク。4並列で直列処理になり、グラフは最後まで永続化されない', '修正1件でも全件の削除・再投入となり、ほぼ全エンティティが再構築される', '全回答の引用が同じファイル名になる', '100MB のアップロード上限（MAX_UPLOAD_SIZE）に近づく可能性', 'F/R の既定設定ではレコード途中で切れ、パイプ表ならヘッダーも失う']
  仮説: 運用上の欠点が大きく、推奨しない。オフライン実験で、境界破損率とチャンク数を B と比較して示すだけでよい。
- E. 期間ごとのレコードファイル（B）＋集計サマリーの別ファイル（設備別プロファイル、月次統計、現象/原因トップN、再発リスト）
  +['件数・ランキング・傾向の質問に、決定的な集計文書で答えられる（検索の限界を補う）', 'ハブ設備の source_id 飽和を、設備プロファイル文書で補える', 'サマリーはアプリで決定的に作れ、LLMコストが小さい（ファイル数は数十から数百）']
  -['データ更新のたびにサマリーを削除・再投入する運用が必要', '生レコードとサマリーの数値が食い違うと混乱する（as of 日付の明記が必須）', '集計軸（設備、現象分類）の正規化が前提']
  仮説: 推奨の第一候補。質問セットのうち集計系の質問は、E では正答率が大きく上がり、単一レコード検索は B と同等になると予想する。
- F. 二層構成: 生レコードは '!'（ベクトルのみ、KGなし）、KG は集計サマリーと帳票だけから作る
  +['数万行分の抽出LLMコストがほぼゼロ（埋め込みのみ）', 'グラフが集計文書と帳票でできるので、ノイズの少ないハブになる', 'naive/mix 検索で生レコードは引ける']
  -['生レコードの細かい関係（設備-部品-原因）がグラフに入らない', 'local/global モードでは生レコードが直接ヒットしない', 'ファイル名ヒントの運用（.[legacy-R!(...)].md）が必要']
  仮説: マルチホップ質問（同じ原因が他の設備でも起きたか）では E よりやや弱いが、コストは1/10以下。E と F を同じ質問セットで比べ、差が小さければ F を採用する。
- G. 固定件数のブロックファイル（例: 500件ごと、_part001）
  +['ファイルサイズと処理時間が均一', '実験のパラメータ（件数）を振りやすい']
  -['途中のレコードが挿入・削除されると以降の境界がずれて、ファイル名と内容が不安定になる（キャッシュも効かない）', '意味的なまとまりがない']
  仮説: 管理番号順で追記のみのデータなら安定する。そうでなければ B（期間）の中で上限件数を超えたときの分割補助として使う。

## current_form_md_evaluation

- 1帳票1ファイル、ラベル付き『項目名: 値』、短い項目を基本情報にまとめ長文を見出しセクションに分ける構造: 良い。4サンプルは143-446文字（約100-340トークン）で、F/R/P のどの経路でも1チャンクになり、帳票全体の文脈が保たれる（実測: 648文字の帳票=480トークン=1チャンク）。native の P でも、兄弟セクションが1500トークン以内に結合される。 → 維持する。1200トークンを超えうるテンプレート（長文が多いもの）に限り、セクション見出しに識別子を入れる。
- H1 タイトル（formats.py:43-44: 最初の string 項目）: 問題あり。修理報告書は『設備修理報告書：R2026-00123』で設備・日付・現象がわからず、点検記録表は『点検記録表：高橋』で人名になっている。P ではタイトルが Section Context として抽出プロンプトに入るため影響が大きい。 → テンプレートに title_fields（報告番号、設備名、設備番号、発生日）を定義し、『# 設備修理報告書 R2026-00123｜CMP装置（EQ-001）｜2026-09-14』のように作る。
- ファイル名 output_basename = {DB id:05d}_{元ファイル名}（formats.py:79-81）: 要改善。1.5.7 の doc_id はファイル名の MD5（pipeline.py:999）で、同名は409になる。DBを作り直すと連番が再利用され、別の文書が同じファイル名になりうる。元のファイル名（scan001、コピー など）は引用で意味をなさない。'.[x]' を含む元ファイル名はヒントとして解釈され、400 になる（routing.py:62）。 → 『{帳票種別}_{報告番号 or file_hash先頭8桁}_{設備番号}_{日付}.md』のように、再現性があり意味のある名前にする。'.[' と ']' を置換する。1.4.x では doc_id は内容 MD5 なので、同じ運用ルール（削除→再投入）を併記する。
- 末尾の『## 原本』（ファイル名、帳票テンプレート＋バージョン、文書ID）と『## 添付画像』の定型文: 問題あり（重要度: 高）。ファイルの24-41%を占める。テンプレート名（全文書でH1と2回）、『原本』、定型文がハブエンティティになり、source_id 200件の上限にすぐ達する。セル座標（J3）や内部ID（文書ID: 1）は無意味なエンティティになりうる。ただし文書IDとファイル名が本文にあるおかげで、別の報告同士の content_hash 重複（pipeline.py:1021-1031）は起きない。 → 末尾を1行『出典: 修理報告書_標準.xlsx（報告番号 R2026-00123）』に縮める。テンプレートのバージョン、DB ID、セル座標、『解析していません』の文は出さない（JSON側に残す）。画像は『添付画像あり（2枚）』程度にする。本文に一意の報告番号があれば、重複誤判定は起きない。
- 値の正規化（_inline は空白の畳み込みだけ。NFKC はラベルにのみ適用）: 問題あり。『ＣＭＰ 装置』のような全角や空白の揺れが残る。LightRAG は全角英数を半角にするが空白の扱いが不統一で（カタカナ間の空白は残る）、NFKC もかけないため、エンティティが分裂する（utils.py:5391）。 → 値に NFKC をかけ、設備番号・設備名・人名を辞書で正規化し、コード形式も統一する（EQ-001）。正規化の前後を JSON に残して監査できるようにする。
- 数値の単位（to_number で『1.5時間』→ 1.5）: 軽微だが要改善。単位のない数値はLLMが意味を取れず、エンティティにも関係にもならない。 → Markdown では単位付きで出す（『作業時間: 1.5時間』）。単位はテンプレートの項目定義に持たせる。
- 関係の明示（箇条書きだけで、設備-現象-原因-処置の文がない）: 改善余地あり（仮説）。長文セクション（故障内容、原因、修理内容）は文なので関係は取れるが、設備番号との結び付きは基本情報の配置から暗黙に推測させている。 → 本文先頭にテンプレート生成の要約文を1文置く（LLM不使用）。A/B 実験（LLM-2）で、トリプルの数と質問への正答率を比較してから採用する。
- 報告者などの人名: 要検討。Person はデフォルトのエンティティ種別なので、人名が多くの設備をつなぐハブになる。空白の揺れ（山田 太郎）は LightRAG 側で吸収されるが、個人情報の観点もある。 → テンプレートの項目ごとに『RAG出力: する/しない/部署に置換』を設定できるようにし、実験 LLM-3 で影響を確認する。
- 抽出欠陥の混入（点検記録表の『判定: 所見』、明細表の欠落）: 問題あり。KG は1行1行を事実として扱い、誤った値は文書を削除しない限り消せない。明細表（異音/振動/油漏れ NG パッキン劣化）が失われると、点検の結果そのものが欠ける。 → Markdown 形式以前の抽出品質の課題として、ストップラベル辞書に『所見』を追加し、明細表に対応する。明細はパイプ表ではなく『- 点検項目: 油漏れ／判定: NG／所見: パッキン劣化』の行形式で出す。AI補完した値や手修正した値には印を付ける。
- 見出しのエスケープ（行頭 # → \#）、UTF-8・BOMなし・LF: 良い。native パーサは ATX 見出しでブロックを分けるので、値中の # を無害化するのは正しい。legacy は UTF-8 限定なので BOM なし UTF-8 で問題ない（extractors.py:180-196）。 → 維持する。加えて、setext 見出しの誤認を防ぐため、値だけの行が『---』や『===』になる場合もエスケープする。
- ドメイン文脈（ライン、工程、設備分類、事業所）の欠如: 要改善。EQ-001 のようなコードは工場やラインをまたいで衝突しうる。分類（搬送系など）の質問は、本文に書かれていないと答えられない。 → マスタシートや設備台帳から、ライン/工程/設備分類を基本情報に追記する。
- 総合評価: 帳票Markdownは『1帳票1チャンク・ラベル付き』という基本設計が LightRAG に合っており、骨格としては及第点。ただし、ファイル名の安定性（1.5.7 の doc_id 仕様）、タイトル、定型文のハブ化、値の正規化の4点は、本格投入の前に直すべき。 → 優先順位: ①ファイル名の安定化と '.[' の除去、②タイトルを識別項目から作る、③末尾の定型文を削減、④値の NFKC と辞書正規化＋単位の保持、⑤要約文の追加（実験後）。

## evaluation_criteria

- チャンク境界の健全性（オフライン）: レコード途中で切れたチャンクの割合 0%、U+FFFD を含むチャンク 0件、列名なしで値だけのチャンク 0件
- チャンク自己完結率（オフライン）: 全チャンクのうち、自分のレコードの管理番号・設備番号・日付を本文に持つ割合（目標 100%）
- チャンクあたりのレコード数とトークンの分布（オフライン）: 中央値と最大値、上限40エンティティを超えそうなチャンク（推定エンティティ数 = レコード数×5）の割合
- LLM コスト見積もり（オフライン）: チャンク数×(1+gleaning)×(システムプロンプト＋チャンク)トークン、ファイル数、想定処理時間（MAX_ASYNC_LLM=4、MAX_PARALLEL_INSERT=3 から算出）
- 定型文比率（オフライン）: 全ファイルに共通する行が全トークンに占める割合（目標 5% 未満）
- 表記ゆれ（オフライン）: NFKC＋辞書適用後の設備名/設備番号の異表記数（目標 0）
- 運用コスト: 1件修正時に削除・再投入する文書数とチャンク数、月次追記時に触るファイル数
- 投入の正しさ（LLM）: doc_status の parse_engine / process_options / chunk_opts / chunks_count が意図どおりか、409/400/DUPLICATE が発生しないか
- グラフ品質（LLM）: 設備エンティティの分裂数（同じ設備が複数ノードになっている数）、ノイズエンティティ（原本、基本情報、テンプレート名、セル座標、文書ID）の数と次数、設備-現象-原因-処置トリプルの再現率（正解付きサンプル50件で手作業評価）
- 検索品質（LLM）: 質問ごとの Recall@CHUNK_TOP_K（正解の管理番号がコンテキストに含まれる割合）。only_need_context=true でコンテキストを取得して機械的に判定
- 回答品質（LLM）: 単一レコード検索は正答率、類似事例は正解集合に対する適合率と再現率、集計は数値の正誤、時系列は順序と日付の正誤、根拠の管理番号・出典ファイルの正しさ、幻覚（存在しない管理番号や数値）の件数
- モード比較: naive / local / hybrid / mix それぞれの上記指標（arXiv 2502.11371 では詳細質問に naive、マルチホップに graph が強いとされる）
- コストと時間（LLM）: 1,000レコードあたりの実測 LLM 呼び出し数、入出力トークン、所要時間から35,000行を外挿

## facts (fact only)

- 【前提・矛盾解消の方針】評価基準は lightrag-hku 1.5.7（PyPI最新、2026-09-02リリース、__api_version__ 0344）のソースコード。1.4.x とは doc_id・チャンクID・パーサ・エンティティ種別設定が根本的に違うため、ユーザーのサーバーのバージョン確認（GET /health または lightrag.__version__）が最優先。資料間の食い違いはコードを優先して解消した（下記の各項目に明記）。
  → アプリの出力仕様は 1.5.7 を主対象とし、1.4.x の場合の差分（doc_id=内容MD5、ENTITY_TYPES環境変数、native mdパーサなし）を注記する。
- .md がどのチャンカーで切られるかはサーバー設定次第。env.example には LIGHTRAG_PARSER=*:native-teP,*:legacy-R がコメントアウトされずに入っている（本セッションで再確認済み、env.example:353）。これをコピーしたサーバーでは .md は native Markdownパーサ＋t（表のLLM解析）＋e（数式）＋P（段落意味チャンク、CHUNK_P_SIZE=2000）になる。未設定なら legacy（UTF-8そのまま読み込み）＋F（1200トークン固定窓、overlap 100）。
  → 同じMarkdownでもチャンク境界がまったく変わる。アプリ側でファイル名ヒント（例: xxx.[legacy-R(chunk_ts=800,chunk_ol=0)].md）を付けるか、推奨サーバー設定を手順書に明記し、doc_statusの metadata.parse_engine / process_options / chunk_opts で実際の経路を確認させる。
- F（固定トークン窓）は見出し・行・レコードを一切考慮しない。日本語では窓の境界が漢字のマルチバイト途中に来て U+FFFD（文字化け）が出る。300レコードの実測では 33チャンク中4チャンクで発生し、レコード途中で切れた。
  → 一覧（表）データを F の既定設定で投入してはならない。短い帳票（1チャンクに収まるもの）なら F でも問題ない。
- R（再帰文字分割）の既定区切りは \n\n, \n, 。, ！, ？, ；, ，, 空白, 文字。読点『、』(U+3001) は含まれない（Web調査の指摘をコードで確認）。空行区切りのレコード列なら、実測でレコード境界どおりに1200トークン以内へ詰められた（33チャンク、493-1190トークン）。
  → レコード間に必ず空行を入れ、1レコード内には空行を入れない（箇条書きは連続行にする）。こうすると R はレコードの途中で切らない。長い文章だけのフィールドは『。』で切られる。
- P（native）は ATX見出し単位のブロックを、parent_headings が同じ兄弟同士で約1500トークン（0.75×2000）まで結合する。チャンクには heading メタデータが付き、抽出プロンプトに『---Section Context---』（最大256トークン）として渡る。ただし結合チャンクの見出しは先頭ブロックのものだけ。チャンク本文や埋め込みには親見出しが入らない。
  → レコードごとに『## 管理番号＋設備＋日付』の見出しを付けても、ベクトル検索に効くのはチャンク本文だけ。各レコードの本文に識別子を書く必要がある。
- native Markdownパーサ（1.5.4-1.5.7）はパイプ表のヘッダー行をチャンク本文から除去する（tables.json にしか残らない）。F/R でパイプ表を切ると、2チャンク目以降に列名が入らない。HTML <thead> ならヘッダーは各スライスに繰り返されるが、トークンが増える。main では PR #3951 で修正済み（2026-09-15マージ）だが未リリース。
  → 一覧データはパイプ表にせず、1行を『- 列名: 値』のレコードブロックとして出力する（source と web の見解が一致）。
- 【矛盾解消】doc_id は 1.5.7 では『ファイル名』の MD5（'doc-'+md5(canonical basename)）で、内容の MD5 ではない。『LightRAGは内容MD5でdoc IDを作る』という現行md評価の前提は 1.4.16 の挙動（lightrag.py:1426）。1.5.7 には別途、正規化テキストの content_hash による重複排除があり、名前が違っても内容が同一なら FAILED [DUPLICATE] になる。同名アップロードは HTTP 409。
  → ファイル名は『論理文書ごとに一意で、DBを作り直しても変わらない』必要がある。現在の {DB id}_{元ファイル名} は、DBリセット後に別文書が同じ名前になる危険がある。更新は必ず『削除→待機→再アップロード』。
- チャンクIDは 1.5.7 では f'{doc_id}-chunk-{order:03d}' で文書内の位置から決まる。1.4.16 は md5(チャンク内容) の全体共通IDで、同一テキストのチャンクが文書間で衝突する。
  → 1.4.x の場合、定型文だけの小チャンク（同一文面）が文書間で衝突するので、定型文を独立チャンクにしない。
- file_path は引用（Reference Document List）専用。抽出LLMはファイル名を見ない。引用はファイル単位で番号付けされ、行やセクション単位にはならない。include_references の既定は False。
  → 大きな一覧を1ファイルにすると、どの回答も同じファイル名を引用する。行単位の出典（管理番号、元ファイル名、行番号）はレコード本文に書く。
- メタデータフィールドやフィルタは存在しない（日付・設備で絞り込めない）。document_date の PR #3805 は未マージ。
  → 日付（ISO＋『2024年4月』のような自然文）、設備番号、設備名、ライン、帳票種別を全レコードの本文に書く。
- 抽出は1チャンクあたり LLM を1回＋gleaning 1回（MAX_GLEANING=1）呼ぶ。1応答の上限は、エンティティ40個（MAX_EXTRACTION_ENTITIES）とエンティティ＋関係の合計100件（MAX_EXTRACTION_RECORDS）。システムプロンプトには数千トークンの例示が入る。
  → 1チャンクにレコードを詰めすぎると、エンティティが黙って欠落する（16件×4-6エンティティで40を超える）。逆に1レコード1チャンクだと呼び出し回数が膨大になる。表レコードは1チャンク3-8件（約400-800トークン）が目安の仮説。
- エンティティは正規化後の名前の完全一致でしか統合されない。normalize_entity_name は漢字間の空白を除く（'山田 太郎'→'山田太郎'）が、カタカナ間の空白は残す（'溶接ロボット R-02'）。全角英数は半角になるが、NFKC はかけないので半角カナや丸数字は別物のまま。自動の表記ゆれ統合は未リリース（#1323、PR #3766）。
  → アプリで NFKC をかけ、設備名・設備番号・人名を辞書で正規化し、全ファイルで同じ表記に揃える。
- ハブエンティティの飽和: source_id は200件まで（SOURCE_IDS_LIMIT_METHOD=KEEP）。上限に達した後の新しいチャンクからの説明は捨てられ、ノードは更新されない。
  → 数千件に登場する設備（例: プレス機No.3）について、グラフの説明は古い200件分で止まる。設備ごとの傾向は、アプリで作る集計文書で補う。
- クエリ時の予算は TOP_K=40、CHUNK_TOP_K=20、MAX_TOTAL_TOKENS=30000、RELATED_CHUNK_NUMBER=5。回答LLMが見るのは多くて数十レコード。
  → 8,000-35,000行を対象にした件数・ランキング・平均・推移の質問は、検索では正しく答えられない。アプリで決定的に集計した文書を別途作るか、SQL/Excel に回す。
- SUMMARY_LANGUAGE の既定は English（env.example:321 で再確認）。エンティティの説明に加え、クエリから抽出するキーワードの言語も決まる。
  → 最初の投入前に SUMMARY_LANGUAGE=Japanese にする（アプリの手順書に記載）。
- 1.5.x で ENTITY_TYPES 環境変数を設定すると起動時に SystemExit する。エンティティ種別は ENTITY_TYPE_PROMPT_FILE（YAML）でカスタマイズする。既定の種別に 設備・部品・現象・原因・処置 はない。
  → 設備保全向けの種別プロファイル（設備, 部品, 不具合現象, 原因, 処置, 工程/ライン, 部署, アラーム）を用意する。JSONモードでは entity_extraction_json_examples が必須。
- レコード単位で正確に区切る手段: POST /documents/text(s) の chunking {strategy:'fixed_token', params:{split_by_character, split_by_character_only:true, chunk_token_size}} を使うと、区切り文字ごとにちょうど1チャンクになる（小さい区間は結合されない。上限を超えるとエラー）。Web UI やアップロードでは、ファイル名ヒントで指定できるのは chunk_ts / chunk_ol / drop_rf だけで、区切り文字はサーバー全体の CHUNK_F_SPLIT_BY_CHARACTER でしか設定できない。【矛盾解消】『split_by_character は Python API のみ』という現行md評価の想定は 1.5.7 では誤り。
  → 手動アップロード運用なら『空行区切りのレコード＋R（chunk_ts 600-800, overlap 0）』が現実的。将来API投入に移るならセパレータ方式に切り替えられるよう、区切り行を一意にしておく。
- ファイル名ヒントの正規表現は \.\[([^\]]*)\](\.[^.]+)$。不正なヒントは HTTP 400。ヒント文字列が空でなければ、ルールのオプションは丸ごと置き換わる（例: '.[legacy-R].md' にすると t が外れる）。
  → output_basename は元ファイル名の '.[' をそのまま残す（_UNSAFE_FILENAME は []. を置換しない）。'.[' を必ず置換し、ヒントはアプリが意図して付けるときだけにする。
- legacy のテキスト読み込みは UTF-8 限定で、CP932 は失敗する。legacy の .xlsx は TSV 風のダンプ（ヘッダーの繰り返しなし）。
  → Excel/CSV を直接投入せず、アプリで UTF-8（BOMなし）の md に変換する方針は正しい。
- 削除はパイプラインが idle のときだけ受け付けられる。共有エンティティは残ったチャンクの抽出キャッシュから再構築される。一括削除でも文書ごとに再構築が走る（RFC #3659）。抽出キャッシュのキーはプロンプト全体のハッシュ。
  → 1行1ファイルは削除・差し替えのコストが最大。巨大1ファイルは1回の修正がグラフ全体に及ぶ。出力はバイト単位で決定的にし（本文にタイムスタンプを入れない）、再投入時にキャッシュが当たるようにする。
- 並列度: MAX_PARALLEL_INSERT=3文書、文書内のチャンク抽出は MAX_ASYNC_LLM=4 並列。グラフの永続化は文書単位。
  → 35,000行を1ファイルにすると4並列でしか進まず、終わるまで何もコミットされない。中サイズのファイルに分けるほうがスループットと障害耐性の点で有利。
- 【矛盾解消】日本語のトークン密度: 資料間で推定がずれていた（0.7-1.3トークン/文字、1-1.3文字/トークン）。o200k_base の実測は 0.71-0.76トークン/文字。帳票1件（648文字）は480トークン、表1レコードは約120トークン。
  → CHUNK_SIZE 1200 はおよそ1,600文字。現行の帳票4サンプル（143-446文字）は約100-340トークンで、どの経路でも1チャンクに収まる。

  → 数万レコード規模なら PostgreSQL などを推奨とサーバー側手順に書く（アプリの範囲外だが前提条件として明記）。
